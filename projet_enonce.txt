
Sujet : Architecture et Traitement de Données Massives (ETL)
Description de la tâche L'objectif est de développer un pipeline de traitement de données
(ETL) capable d'ingérer, de nettoyer et d'unifier trois sources de données publiques
hétérogènes. Le volume total des données brutes dépasse la capacité de la mémoire vive (RAM)
d'une machine standard, imposant l'utilisation de techniques de traitement par flux (streaming),
par lots (chunking) ou l'usage d'un moteur de base de données optimisé sur disque.
Les étudiants doivent produire une base de données unifiée permettant de croiser les
informations légales des entreprises, les données des associations et leur localisation
géographique précise.
Objectifs techniques
1. Ingestion & Optimisation Mémoire : Concevoir un script capable de lire des fichiers
CSV volumineux (> 5 Go) sans provoquer de dépassement de mémoire (OOM).
2. Normalisation : Harmoniser les schémas de données disparates (types de colonnes,
encodages, formats de dates).
3. Jointure Complexe : Réaliser des jointures entre les datasets sur des clés communes
(SIREN/SIRET) et des clés géographiques (Code Postal + Adresse).
4. Indexation : Structurer la donnée finale pour garantir des temps de réponse inférieurs
à la seconde sur des requêtes d'agrégation.
Sources de Données (Fichiers requis)
Les étudiants doivent télécharger et traiter exclusivement les fichiers bruts suivants :
• Source 1 : Base SIRENE (Stock des établissements)
o Description : Données de référence sur les entreprises et établissements en
France (actifs et fermés).
o Fichier : StockEtablissement_utf8.zip
o URL : https://www.data.gouv.fr/fr/datasets/base-sirene-desentreprises-et-de-leurs-etablissements-siren-siret/
• Source 2 : Répertoire National des Associations (RNA)
o Description : Liste exhaustive des associations loi 1901.
o Fichier : rna_waldec.zip (Dernier millésime disponible).
o URL : https://www.data.gouv.fr/fr/datasets/repertoire-nationaldes-associations/

o Description : Référentiel géolocalisé de toutes les adresses françaises.
o Fichier : adresses-france.csv.gz (Format CSV, couverture France entière).
o URL : https://adresse.data.gouv.fr/donnees-nationales
⚠ NOTE TECHNIQUE IMPORTANTE
1. Gestion des sources et décompression Les données sources sont fournies dans des formats
d'archive compressés (.zip, .gz). Il est fréquent que ces archives contiennent plusieurs fichiers
ou que les données soient fragmentées. L'étape d'extraction, de décompression et de
reconstitution des flux est un prérequis technique obligatoire. Vous ne trouverez aucun fichier
"prêt à l'emploi".
2. Hygiène des données (Data Cleaning) La propreté des données est de votre entière
responsabilité. Vous devez anticiper et traiter les anomalies classiques :
• Problèmes d'encodage (UTF-8 vs Latin-1).
• Incohérences de séparateurs (point-virgule vs virgule).
• Gestion des guillemets et des caractères spéciaux.
• Traitement des valeurs nulles ou aberrantes.
3. Choix de l'architecture (Base de Données) Vous avez une liberté totale quant au choix de
la technologie de stockage (PostgreSQL, MySQL, SQLite, DuckDB, MongoDB, solution
NoSQL, fichiers Parquet optimisés, etc.). Votre architecture sera jugée sur sa pertinence et sa
performance : la solution choisie doit permettre de répondre aux requêtes d'analyse sans latence
excessive malgré la volumétrie importante.

2. 2. Le Score Challenge (Classement)
Ce score est purement automatisé et sert uniquement à départager les équipes pour
le podium.
Le classement est établi par un script de "Stress Test" qui enverra une rafale de 500
requêtes variées (simples, moyennes, complexes) à votre API.
Le Barème (Total Standard : 1000 points / Max Théorique : 1250 points)
Le score se divise en deux parties cumulables pour chaque requête :
Partie A : Justesse (Correctness) — Sur 500 points
C'est la base : votre API renvoie-t-elle la bonne donnée ?
• Réponse Correcte : +1 point
• Réponse Fausse ou Erreur 500 : 0 point (et 0 point en vitesse)
Partie B : Rapidité (Speed) — Sur 500 points (base) à 750 points (bonus)
Si et seulement si la réponse est correcte, des points de performance sont attribués
en fonction du Temps de Réponse Net (après déduction du Ping moyen).
Temps de Réponse Net Points de Vitesse
< 500 ms (Performance Élite) 1.5 point (BONUS) 🚀
< 1 seconde 1 point
< 3 secondes 0.75 point
< 5 secondes 0.5 point
< 20 secondes 0.1 point
> 20 secondes 0 point (Timeout)
Note Technique :
Le total "parfait" standard (tout juste en moins d'une seconde) est de 1000 points.
Cependant, grâce au bonus de rapidité (< 500ms), le score maximal théorique est de
1250 points.
⚠ Gestion de la Latence Réseau (Ping Adjustment)
Pour garantir l'équité, notre script mesure la latence réseau (Ping ICMP) vers votre
serveur avant le test.
Cette latence moyenne est déduite de votre temps de réponse brut.
Exemple : Si votre serveur répond en 540 ms (Brut) et que le Ping moyen est de 60
ms, le Temps Net retenu est de 480 ms. Vous obtenez donc le bonus de 1.5 point.
Votre serveur DOIT autoriser le protocole ICMP (Ping) pour bénéficier de cette
déduction.

1. Endpoint : "Fiche d'Identité Unifiée" (Le Golden Record)
Cet endpoint est le cœur du challenge. Il doit retourner un objet JSON fusionnant les attributs
légaux (SIRENE), associatifs (RNA) et géographiques (BAN).
• Route : GET /siret/{siret}
• Méthode : GET
• Paramètre : siret (String, 14 caractères numériques).
✅
Scénario de Test : La "Preuve par 3"
Nous allons tester un SIRET correspondant à une Association Employeuse.
• Sujet : "LA CROIX ROUGE FRANCAISE" (SIRET: 77567227200020)
• Pourquoi ce test est critique ?
1. Si vous n'avez que SIRENE : Vous aurez le nom, mais pas l'ID RNA (W...).
2. Si vous n'avez que RNA : Vous n'aurez pas ce SIRET précis (car le RNA lie
souvent au siège, pas à l'établissement secondaire).
3. Si vous n'avez pas BAN : Vous n'aurez pas les coordonnées GPS (lat, lon).
Exemple de Réponse Attendue (200 OK) :
JSON
{
"identity": {
"siret": "77567227200020",
"nom_raison_sociale": "CROIX ROUGE FRANCAISE",
"enseigne": null,
"categorie_entreprise": "PME"
},
"asso_id": {
"id_rna": "W751000060", // PREUVE 1 : Croisement SIRENE <-> RNA réussi
"date_publication_jo": "1901-07-01"
},
"location": {
"numero_voie": "98",
"type_voie": "RUE",
"libelle_voie": "DIDOT",
"code_postal": "75014",
"commune": "PARIS",
"geo_score": 0.98,
"latitude": 48.8296, // PREUVE 2 : Croisement SIRENE <-> BAN réussi
"longitude": 2.3235
}
} ⚠
Critère d'échec :
• Si le champ id_rna est null ou absent pour ce SIRET -> 0 point.
• Si les champs latitude / longitude sont absents -> 0 point.

4. Codes d'Erreur Standardisés
Pour que le script de correction automatique ne plante pas, les erreurs doivent suivre ce format
strict :
• 404 Not Found : Si le SIRET n'existe pas.
JSON
{ "error": "SIRET_NOT_FOUND", "message": "Le siret 00000... est
inconnu." }
• 400 Bad Request : Si le format du paramètre est invalide (ex: SIRET de 12 chiffres).
JSON
{ "error": "INVALID_FORMAT", "message": "Le siret doit contenir 14
chiffres." }
Résumé pour les Étudiants : "Comment avoir 20/20 à l'API ?"
1. Justesse (Correctness) : Pour le SIRET de la Croix Rouge (Exemple 1), si votre JSON
ne contient pas à la fois le SIRET et le numéro RNA (W...), c'est que votre jointure a
échoué.
2. Complétude : Si votre JSON ne renvoie pas de latitude/longitude, c'est que vous n'avez
pas croisé avec la BAN.
3. Rapidité : Si l'endpoint /stats met plus de 1 seconde à répondre, c'est que vous n'avez
pas mis d'INDEX sur la colonne code_postal de votre base de données.
