1. Objectif & Périmètre
L'objectif est de construire un référentiel unifié des organisations en France en
croisant trois sources officielles.
• SIRENE (INSEE) : Entreprises & établissements (Stock + Historique).
• RNA (Ministère de l'Intérieur) : Associations loi 1901 (Fichier rna_waldec).
• BAN (IGN) : Référentiel national des adresses.
Rappel : Les formats JSON de l'API, les seuils de performance et le protocole de
stress-test (500 requêtes) décrits dans le sujet principal doivent être strictement
respectés.

4. Pipeline de Données (Data Engineering)
4.1 Ingestion & Conversion
1. Téléchargement : Récupérer les fichiers bruts (SIRENE Stock, RNA Waldec,
BAN France entière).
2. Conversion Immédiate : Décompresser et convertir les CSV en Parquet.
o Conseil : Caster les types (int, string) dès cette étape pour réduire la
taille.
o Log : Conserver un journal d'ingestion (nombre de lignes, erreurs).
4.2 Normalisation (Focus BAN)
• Tokenisation : Séparer numero, type_voie, libelle, code_postal, commune.
• Standardisation : Harmoniser les abréviations (ex: "Av." $\rightarrow$
"AVENUE", "St" $\rightarrow$ "SAINT").
• Validité : Vérifier la cohérence CP $\leftrightarrow$ Commune.
4.3 Appariement (Matching SIRENE ↔ RNA)
• Stratégie de Blocage : Ne comparer que si le code_postal est identique.
• Fuzzy Matching : Comparer la raison sociale (SIRENE) et le titre (RNA).
Générer un score de confiance [0-1].
• Livrable Intermédiaire : Une table de liaison (Journal d'appariement)
contenant : siret, id_rna, score, methode.
⚠ Le Cas d'Or (Gold Case) :
L'entité Croix-Rouge Française (SIRET 77567227200020) doit impérativement
ressortir avec un ID RNA non nul et une adresse validée BAN. C'est le test de
passage.
5. Architecture des Vues & API
Plutôt que de faire des calculs en temps réel, pré-calculez des vues optimisées :
1. golden_record (Parquet/DuckDB) : Table finale plate. Clé unique : siret.
Contient les infos fusionnées SIRENE + RNA + BAN. Sert l'endpoint
/siret/{siret}.CONFIDENTIAL
2. search_view (SQLite FTS5) : Table dédiée à la recherche textuelle. Contient
uniquement : id, text_search_vector, postal_code. Sert l'endpoint /search.
3. stats_view (Parquet) : Table pré-agrégée par code postal. Contient les totaux
et les tops NAF. Sert l'endpoint /stats/{cp}.
6. Performance & Objectifs (SLA)
Le Stress-Test : 500 requêtes lancées en rafale.
• Ping ICMP déduit du temps de réponse.
• Bonus si réponse < 500ms.
Cibles à viser (p95) :
• /siret/{siret} : < 200 ms (Lecture simple clé/valeur).
• /search : < 1 s (Grâce à l'index FTS5).
• /stats/{cp} : < 500 ms (Lecture d'une ligne pré-calculée).

9. Critères de Validation
1. Conformité JSON : Les clés, types et nullables doivent être identiques à la
spécification.
2. Reproductibilité : Le projet doit s'installer (requirements.txt) et se lancer via
make.
3. Honnêteté Intellectuelle : L'usage d'IA pour coder est autorisé. L'usage
d'API externes pour récupérer la donnée est interdit.
4. Justesse : Les cas "Gold" (Croix-Rouge, mairies, etc.) font foi pour la note de
correctness.
